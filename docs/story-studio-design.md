# 故事工作室设计

> 状态：持续演进的产品与架构设计。本文描述故事工程编辑体验的目标，不表示所有界面均已实现。当前运行机制见 [故事工程与多人物写作流水线](story-engine.md)。

## 目标

故事工作室帮助玩家维护一部长期故事，而不是编辑故事引擎的内部字段。人物、剧情节点、伏笔、事实、事件、资料和输出分区应作为可识别、可关联、可检查的创作对象出现；模型运行参数和 Session 记录不占据主创作界面。

工作室必须让玩家直接回答这些问题：

- 故事正在走向哪里，哪些情节已经发生？
- 哪个伏笔在哪里埋设，计划在哪里回收？
- 某个人物此刻知道什么，为什么知道？
- 当前结论来自哪段原著或哪次网络研究？
- 下一轮会生成哪些正文分区，各自承担什么职责？
- AI 提议改变了什么，哪些内容仍未被玩家接受？

## 当前界面的问题

格式 0 编辑器验证了存储、会话绑定和流水线能够运行，但它把数据模型直接投影成长表单：

- 左栏只切换工程，单工程时几乎没有价值；工程名称和开发验收数据被当作主要导航内容。
- 大纲、伏笔、提案、历史与人物知识都表现为大文本框，关系、状态、时间和可见范围只能藏在自然语言中。
- “仅导演可见”“不会自动改写”等括号说明暴露实现限制，却没有提供对应的可见范围或接受操作。
- Worker provider、model 和并发数先于故事内容出现，运行设置干扰创作。
- 历史文本混入持久化 marker；内部幂等机制泄漏到用户内容。
- 人物认知虽然在模型输入层隔离，但玩家无法方便地检查一条知识的来源或用某个人物的视角预览上下文。
- 页面是一条无法建立空间记忆的纵向滚动流；内容增长后无法浏览长期故事。

这些问题不能用重新配色、折叠表单或增加说明文字解决。编辑器需要以创作对象及其关系为中心重新建模。

## 设计原则

1. **显示故事对象，不显示存储字段。** 玩家操作剧情节点、人物、事实、事件、资料和输出卡片；文件格式与幂等标记留在实现层。
2. **关系具有类型。** 先后、因果、伏笔埋设与回收、人物知情、事件观察和资料引用不能都退化成无语义连线。
3. **同一模型提供多种视图。** 剧情图适合空间关系，时间线适合已发生事件，阅读器适合原著，排序卡片适合输出布局；不把所有对象强塞进一张无限画布。
4. **人物认知必须可检查。** 选择人物后能够看到该人物会收到的事实及其证据；输入隔离既是运行规则，也是产品可见能力。
5. **AI 建议不是正式事实。** 模型产生的剧情与伏笔建议以候选变更出现，玩家接受后才进入正式故事图。
6. **用交互表达规则。** 可见范围使用徽标或过滤视图，建议使用接受与拒绝操作，运行状态使用阶段条；避免以括号堆叠负面保证。
7. **创作与运行设置分层。** 模型路由、并发和失败详情进入设置或可折叠执行抽屉，不占据故事主视图。
8. **成熟组件承载通用交互。** 节点拖放、连线、缩放、框选和视口管理不自行实现；项目只拥有故事语义和 DSH 集成。

## 信息架构

桌面端使用三栏布局，底部保留可折叠执行状态：

```text
┌ 项目菜单 / 当前会话       故事地图  时间线  人物  资料  输出布局 ┐
├───────────────────────────────────────────────────────────────┤
│ 故事导航树        │              主工作区              │ 属性面板 │
│                   │                                    │          │
│ ▾ 故事结构        │     节点画布 / 时间线 / 阅读器      │ 标题     │
│   故事地图        │                                    │ 状态     │
│   时间线          │       ○ 场景 ───→ ○ 场景          │ 可见范围 │
│ ▾ 人物            │          ╲                        │ 详细内容 │
│   阿梨            │           埋设 ───→ 回收          │ 关联对象 │
│   柏舟            │                                    │          │
│ ▾ 资料库          │                                    │          │
│ ▾ 输出布局        │                                    │          │
├───────────────────────────────────────────────────────────────┤
│ 研究 → 人物 → 导演 → 分区 → 编辑                 运行状态/详情 │
└───────────────────────────────────────────────────────────────┘
```

工程切换位于顶部项目菜单或独立首页。左栏属于当前工程，展开人物、资料、故事视图和输出配置；点击对象后切换中央视图并在右侧显示属性。窄屏按“导航 → 主视图 → 属性抽屉”逐层进入，不压缩三栏。

## 故事地图

故事地图使用可自由放置的类型化节点和连线，但不是无约束白板。

第一版节点包括：

- **篇章**：幕、章节或支线的分组容器。
- **剧情节点**：计划或已经发生的场景、转折与决定。
- **秘密**：尚不能归入具体场景的谜团、真相或悬念。

第一版关系包括：

- **先于**：规定叙事顺序或前置条件。
- **导致**：表达因果。
- **埋设 → 回收**：连接伏笔出现与兑现的位置。

故事簇层级不是一条普通关系。节点只通过父级字段归入篇章或场景，画布和 Worker 都从这份层级投影；不再同时维护“属于”连线，避免移动节点后出现两个互相矛盾的归属来源。

原著或研究依据不伪装成节点之间的关系。它保存为独立资料引用，直接关联剧情节点或人物事实，并携带原文位置和引用快照。

伏笔优先表现为“埋设剧情节点 → 回收剧情节点”的关系，而不是独立大文本框。关系记录未埋设、已埋设、已触发、已回收或已放弃状态、目标篇章、可见范围和简短备注。缺少具体一端时可以先连接秘密节点，待剧情明确后再改连线。

顶层节点卡显示标题、折叠摘要、类型、状态和内部对象计数；篇章或场景可以成为故事簇，默认折叠内部的场景、秘密和事实，展开后按层级显示并允许直接进入属性面板。详细内容、参与人物、创作范围、默认认知策略与引用在右侧属性面板编辑。画布需要平移、缩放、框选、多选、复制、撤销、重做、MiniMap 和可选自动布局。

## 人物与认知

左栏的人物条目直接打开该人物的中央工作区。人物设定、当前动态、认知与经历、Agent 输入分别占据清晰页面；人物页顶部直接投影当前位置、状态和目标。角色卡 `scenario` 是人物进入本局时的对话情境，不冒充随回合变化的当前状态；世界事件、连续性记录或玩家修订共同维护当前动态。故事簇继续提供默认认知策略，单条事实可以继承或转成精确覆盖。全局人物乘事实矩阵只在需要横向排查时作为高级认知审计展开，不再挤占人物主任务。

每条人物事实至少记录：

- 事实文本；
- 知情人物集合；
- 来源事件或玩家手工输入；
- 对应最终正文证据；
- 获得回合与当前有效性；
- 是否公开、被推测、被否定或仍不确定。

选择“以此人物查看”时，不可见事实被隐藏或变暗；“预览 Worker 输入”展示下一轮该人物实际会接收的档案、场地状态、事实与本轮公共输入。模型上下文从结构化人物字段和事实记录编译，不再依赖一段无法追溯的累计知识文本。

场景参与是剧情节点或当前场景的关系，不再是人物表单里的永久复选框。人物进入、离开和位置变化成为事件，从而约束连续性 Worker 可以建议哪些观察。参与本身不授予知识；故事簇必须明确选择“参与人物可知”策略，或由单条事实精确指定知情人物。事件来源事实显示对应回合和事件，事件属性面板也反向列出由它形成的事实，使故事图、时间线与认知矩阵可以双向核对。

## 时间线与故事事实

“全局剧情账本”改为事件时间线。每个完成回合产生一个或多个事件卡，记录时间、地点、参与人物、公开事实、最终正文证据和关联剧情节点。人物观察以事实关系连接事件，不在历史 Markdown 中复制内部 marker。

玩家可以修正事件摘要、参与者和知情范围。原始 Session 事件继续作为可重放证据，但只在调试视图显示。面向读者的“历史”正文分区属于输出布局，不与内部事件时间线混用。

## AI 建议

AI 产生的剧情、大纲或伏笔建议进入建议收件箱，并以半透明候选节点和虚线关系叠加在故事地图上。每组建议支持：

- 接受；
- 修改后接受；
- 拒绝；
- 暂存。

接受操作形成可撤销的结构化变更；拒绝不会污染正式图。建议必须说明依据的事件、人物行动或资料引用。界面不再显示“待审提案不会自动改写……”之类的说明，因为候选视觉与接受操作已经表达其状态。

## 原著与研究资料

资料视图由目录、阅读器和引用面板组成。资料保留章节与段落位置，支持搜索、相邻段落展开、书签和引用；剧情节点、人物事实和研究结论可以链接到具体原文片段。

资料正文只有一份，阅读器根据 Markdown 标题和自然段投影出有界段落，不复制第二份章节正文。引用保存资料标识、段落位置、原文快照、说明和可选关联对象；资料后来被修改时，旧快照继续作为当时采用该依据的记录，并明确提示已经无法在当前原文中定位。

网络结果先进入研究收件箱，保留 URL、标题、摘要、原始查询、Session、回合与搜索结果事件位置。确认后才能成为长期资料；忽略不会改变正式资料。研究 Worker 可以在有界次数内搜索本地原著、展开相邻段落和追加网络查询，每条结论携带来源；无来源推测必须与事实分开。

## 输出布局

输出分区使用可拖动排序的卡片，而不是关系图：

```text
☰ 主正文          prose       已启用
☰ 柏舟视角        character   柏舟
☰ 前情回顾        history     已启用
```

卡片属性包括职责、目标人物、启用状态、篇幅与风格。输出卡可以引用剧情节点或篇章，但不需要在故事地图中占据长期位置。多卡按可见顺序进入分区 Worker 和最终编辑。

## 执行状态与设置

底部阶段条只显示当前运行状态：

```text
研究 ✓  人物 2/2 ✓  导演 ✓  分区 3/3 ✓  编辑中…
```

展开后才显示模型、耗时、失败和重试入口。Worker provider、model、并发、每阶段模型与预算进入项目设置。正常创作界面不展示 Session event 名称、revision、文件 marker 或 Host 能力诊断。

## 组件选择

故事地图首选 `@xyflow/react`。它兼容当前 React 18，采用 MIT 许可，并提供受控节点与边、自定义节点、连线、拖放、缩放、选择、分组、MiniMap 和视口管理。项目负责节点和关系的故事语义，不拥有通用画布基础设施。

tldraw 或 Excalidraw 不作为正式故事模型的核心。自由画布适合草图，却难以可靠编译“谁知道事实”“关系是因果还是伏笔”“本轮是否允许使用”等模型输入；以后可以作为不进入流水线的草图层。

节点详细内容继续使用 Markdown 存储。第一轮不因编辑器外观引入复杂富文本格式；属性面板可以先采用清晰的 Markdown 编辑器，待真实长文编辑反馈后再选择富文本组件。

## 建议的数据模型

画布不能只是格式 0 四个 Markdown 字段的外观包装。下一版需要类型化索引与可编辑正文并存：

```text
story.json                    节点、关系、位置和状态
nodes/<node-id>.md            节点详细内容
characters/<id>/description.md
characters/<id>/personality.md
characters/<id>/scenario.md
characters/<id>/example-dialogue.md
characters/<id>/system-prompt.md
characters/<id>/post-history-instructions.md
sources/<source-id>.md        章节、片段与引用正文
outputs/<output-id>.md        分区写作职责
```

现有 Session 绑定、原子写入、revision、路径约束、多 Agent 阶段、失败降级和重放记录继续保留。故事工作区协议、编辑器、人物上下文编译和连续性结果需要围绕新模型重构。格式迁移方案在实现前单独确定；不能为保留开发验收数据而长期维持两套创作模型。

## 已完成的首个实现纵切片

1. 建立三栏工作室框架、项目菜单和视图切换，移除创作主界面的运行参数与内部术语。
2. 使用 `@xyflow/react` 实现篇章、剧情节点、秘密以及先后、因果、埋设与回收关系。
3. 实现人物事实、知情范围和“以此人物查看 / 预览 Worker 输入”。
4. 把连续性输出改为带正文证据的事件和人物事实建议。
5. 将 AI 建议呈现为候选节点与关系，并支持接受、修改和拒绝。
6. 将输出分区改为可排序卡片，并把现有故事流水线编译到新模型。

资料阅读器、段落级引用、相邻段落自动展开、研究收件箱和研究 Worker 主动发起的多轮有界追查已在后续纵切片接入。研究结论现在携带运行时校验过的证据编号；无效引用会降为不确定项，不能冒充明确事实。

## 验收标准

- 主界面不存在从大纲一路滚动到资料库的单列长表单。
- 单工程时左栏仍能用于导航人物、故事、资料和输出对象。
- 玩家可以在十秒内新增剧情节点并连接一条伏笔埋设与回收关系。
- 选择任一人物即可看到下一轮该人物实际可用的知识及其来源。
- AI 建议与正式故事对象视觉上明确分离，未接受建议不会进入模型的正式大纲。
- 回合完成后，事件出现在时间线；人物事实只能引用实际可见正文和明确观察关系。
- 网络结果首先出现在研究收件箱，未接受结果不会成为后续回合的正式资料；收为资料后仍能查看原始 URL 与查询来源。
- 研究 Worker 只有在首批证据不足时才追加本地或网络查询；查询不会重复或超过项目设置的轮数，明确事实必须引用本轮真正提供过的证据编号。
- 项目设置以外不出现 worker provider、revision、Session event 或内部 marker。
- 故事图、时间线、人物认知和输出布局编译出的模型输入能够从 Session 与工程文件重建。

## 反馈记录

2026-08-27 的首次真实页面反馈指出：左栏没有承载故事结构，开发验收工程名不应成为主要内容；大纲、伏笔、提案和历史使用大文本框既难看也无法表达关系；“不会自动改写”等括号说明使界面显得尴尬；画布与节点关系可能更符合创作思维，但不应把所有内容强制放进一张思维导图。这些反馈确定了三栏工作室、类型化故事图、多视图和候选变更机制的方向。

同日纵切片验收确认了两个交互约束：480×820 下必须能进入全部工作面并独立开关属性面板，不能依赖桌面左栏；输出卡不能只依赖 HTML5 拖放，因为触屏、键盘和自动化输入并不共享可靠的 drop 事件。输出顺序因此同时提供拖动与上下移动操作，两者写入同一正式顺序。

同日资料阅读器验收发现，平板宽度的属性面板覆盖了中央工作区，使段落引用按钮存在于可访问树却不可见、点击也落到面板控件。980px 以下的布局因此改为可收缩的三列，只有手机宽度使用属性抽屉；手机关闭抽屉时单独清除对象选择，保留当前资料阅读位置。页面环境还可能不提供 Web Crypto，故事对象标识改用不承担安全用途的客户端 UUID 生成器；安全令牌不使用该回退。

同日研究链路审查发现，网络搜索结果虽然进入当轮研究简报，却在回合后消失，玩家无法判断哪些结果值得长期保留；`web` 类型的查询范围还会混入本地摘录，看起来像事实。研究结果因此先进入可接受或忽略的收件箱，接受后才创建带来源记录的正式资料；本地检索排除查询范围，并自动携带命中段落的相邻上下文。

同日继续审查发现，只要启用 Web 资料就每轮固定搜索一次既浪费请求，也不是真正的研究 Agent；一次自由文本研究还无法说明结论来自哪里。研究阶段因此先读取公开历史、近期会话和本地资料，再由 Worker 以结构化决策请求必要的本地或网络追查。每轮最多两条查询，总轮数由项目设置限制；明确事实只接受实际输入过的证据编号，错误引用自动降为不确定项，格式失败则停止追查并保留已有证据。

同日真实页面验收确认，升级前保存的故事会得到默认两轮研究而无需迁移操作；项目设置显示 1–4 的轮数范围。480×820 下该设置与保存、连接和删除入口仍在同一个纵向抽屉内可见，没有把执行参数重新放回创作主工作区。

同日连续性输出审查发现，自由文本“剧情建议”和“伏笔建议”即使显示为卡片，仍会在进入画布前丢失节点种类、参与人物和彼此关系，玩家只能逐条整理。连续性 Worker 因此直接提出类型化候选节点与先后、因果、所属或伏笔关系；关系可以连接已有正式节点或同批候选节点。候选节点和关系携带同一来源事件，界面用候选样式与接受、拒绝操作表达状态；关系只有在两端节点都成为正式节点后才能接受。

同日候选关系的真实页面验收发现，手机断点把三栏 Grid 切换为普通块布局后，外壳虽然占满剩余高度，中央工作区却没有继承该高度，导致 480×820 下节点存在于 DOM 但整个画布高度为零。手机布局因此显式把外壳高度传给主工作区；复验确认画布、节点、关系、工具栏和属性抽屉均可见。该问题说明窄屏验收不能只检查入口是否存在，还必须检查主要工作面的实际尺寸和可见内容。

同日人物页验收发现，把事实分别塞进每个人物属性栏会隐藏人物之间的认知差异，也容易让“参与事件”被误解为“知道事件”。人物事实因此移到中央认知矩阵，以事实为行、人物为列直接编辑 `knownBy`；Persona 和 Worker 输入预览仍留在人物属性面板。真实页面中，把一条共享事实分配给新增人物后，其 Worker 输入立即出现该事实；只分配给该人物的私有事实没有进入另一人物的输入。事件来源链接能够从事实进入对应时间线，事件属性面板也能返回认知矩阵。480×820 下矩阵改为逐条事实卡片，人物属性抽屉可独立开关且关闭后仍回到原视图。

同日后续反馈指出，人物、故事节点和事实仍像彼此脱钩的几套编辑器；画布缺少默认折叠的内部层级，拖动节点时连线文字闪烁，新增信息还需要反复手工同步知情范围。格式 2 因此把父级故事簇、折叠摘要和默认认知策略放入节点，把事实关联到节点并区分继承与精确覆盖。画布只投影顶层故事簇，展开后显示任意深度的可知子节点与内部事实；人物视角从同一有效认知结果投影，并遮住仅为导航而显示的未知祖先摘要。拖动位置只在结束时写回正式工作区，避免每个指针帧重建全部节点与连线。

同日连续性链路审查发现，Worker 仍分别返回每个人物一条观察、节点数组和关系数组；共享观察会重复成多条事实，节点所属只能另建“属于”关系，节点摘要与默认认知还要玩家二次补录。连续性输出因此收束为一个 `changes` 对象：事实直接携带完整知情人物集合，相同文本自动合并；候选节点同时携带父级、摘要、参与人物和认知策略；关系只表达先后、因果和伏笔。候选子节点必须在上级故事簇接受后才能转正，避免正式数据悬挂在候选层级下。

后续反馈应记录它改变了哪项设计原则、对象语义或验收标准。纯视觉偏好可以进入设计令牌与组件实现，不应绕过故事数据模型成为孤立特例。

同日飞行棋验收用例把“故事”边界扩展成“游玩场地”：角色卡应是可复用的稳定人物身份，本局人物实例承载私有认知与临时状态，世界书既可以是普通提示词资料，也可以升级为拥有状态、规则、动作、事件、模型投影和原生界面的可执行世界模块。故事地图、人物认知、资料与输出不是与棋局平行的另一套工具，而是同一场地对世界事件的创作投影。首个纵切片因此让飞行棋状态只能经 Host 动作演进，让人物和导演从模块接口得到不同投影，并允许空白会话直接从场地启动；后续游戏、跑团或经营模块应复用同一注册与投影接缝，而不是向普通世界书增加专用字段。

同日人物页复验发现，人物主体仍被放在右侧属性栏，中央区域却被人物乘事实的认知矩阵占满；人数和事实增长会让日常编辑不断横向膨胀，角色卡与本局状态也继续混在一个误称为 Persona 的文本框中。人物页因此改为以当前人物为中央主体，按人物设定、当前动态、认知与经历、Agent 输入组织；角色卡快照保留 SillyTavern 已验证的描述、性格、`scenario`、示例对话、系统指令和历史后指令，其中 `scenario` 明确作为入场情境，本局位置、状态、目标和备注由独立的当前动态承载。事实的来源节点、事件和知情范围继续作为权威数据，全局矩阵降级为高级认知审计，不再承担人物主编辑器职责。

后续飞行棋验收发现，可执行世界虽然阻止正文伪造骰点和棋子位置，人物仍只是对玩家已经点完的棋局发表评论，没有真正成为场地参与者。世界模块因此增加当前人物回合投影，只给出合法、稳定的动作 id 及说明，执行载荷不进入模型；人物行动 Worker 只能从中选择，Host 执行后把幂等收据与世界状态一起保存。验收必须证明人物私有输入不含其他人物档案、一个规则回合可以包含掷骰和后续选子，并且同一 Session 回合重试不会重复推进。

人物开始执行规则动作后，世界事件与正文事件不能分别形成两份可编辑事实。完成的正文事件因此只保存它覆盖的世界事件序号；时间线从权威世界投影对应标题和结算内容，在正文卡下展示规则来源，并单列尚未关联正文的规则事件。世界事件检查器保持只读，允许反向打开引用它的正文回合或返回游玩场地。

飞行棋连续对白验收还发现，完整对话段落虽然带有说话人标签，运行时仍把双方原句装进同一个人物证据块，再依赖提示词区分归属；严格审校拒绝泛化对白后，导演动作也可能留下等待开口、迎上目光等无对白铺垫。语气证据因此在进入 Worker 前按说话人拆成目标人物原句、对手接话上下文和资料分析，代码只把确实含目标人物原句的证据作为声音锚点；声音阶段的通过数量同时进入分区方案，未通过对白及其专属铺垫必须一起收束。

同一轮验收还发现，研究 Worker 只读取累计的公开时间线时，会把较早回合的“尚未行动”误认成当前状态，并为已经由世界程序结算的旧问题发起追加查询。研究阶段因此把当前权威世界状态和本轮结算作为带稳定编号的首要证据，与旧时间线明确分层；资料检索查询也同时使用当前状态。研究结论可以引用旧事件，但不能用它覆盖当前状态或重复追查权威证据已经回答的问题。

修复后的下一回合证明研究简报已经回到当前状态，却又暴露出正文锚点仍由模型维持：编辑 Worker 删除了带虚构细节的行动人段落后，只留下另一人物换手的次要动作，导致公开记录正确而正文没有表现真正的规则执行者。世界模块因此增加事件到最小叙事首段的确定性投影；Host 把它放进第一个正文分区并在编辑后重新校验。人物、导演和分区 Worker 只补充有决定、关系或获准对白价值的内容，不能再用看向、换手或敲碰物件替代权威事件；所有人物 action 为空且没有对白通过审校时，代码直接省略额外正文生成，避免模型为“什么也没有发生”补出一段微动作。

纯世界回合的最终正文若与 Host 生成的权威首段和公开记录完全一致，连续性阶段也没有可推断的新内容。此时再次请求模型只会增加成本，并可能把规则状态抄成人物目标或重复事实；运行器因此直接把已引用的世界事件沉淀为故事事件，保留研究结果入箱，但不生成角色状态、事实或剧情建议。只有实际可见正文加入人物反应，或者下游改写了准备稿，才调用连续性 Worker。

## 设计判断框架

故事工作室不是“给现有表单换成思维导图”，而是把长期故事创作拆成相互关联、各有合适操作方式的工作面。顶层项目菜单负责选择故事工程；左栏负责在故事、人物、资料和输出对象之间导航；中央区域按对象语义切换故事图、时间线、人物视角、资料阅读器和排序卡片；右侧属性面板只编辑当前选择；执行进度和模型设置留在次要层级。任何新功能都应先确定属于哪一层，而不是继续向同一页面追加输入框。

是否采用画布取决于关系是否是该对象的主要信息。剧情先后、因果、伏笔埋设与回收适合节点和类型化连线；人物已经知道的事实适合按人物过滤的证据列表或认知视图；已发生内容适合时间线；原著适合阅读器和段落引用；输出分区适合排序卡片。空间自由本身不是目标，能够直接看见并修改故事语义才是目标。

正式故事数据、AI 候选和运行证据是三个不同层次。正式数据是下一轮写作的依据；AI 生成的节点、关系和事实先作为候选，只有接受后才进入正式数据；Session 事件、失败详情和模型调用用于重建与诊断，不占据创作主界面。界面应通过位置、样式和操作表达这三者的差别，避免用括号说明实现限制。

人物认知隔离既是模型输入规则，也是必须能由玩家核验的产品能力。人物事实需要来源、正文证据、知情人物和有效状态；“以此人物查看”和 Worker 输入预览应从同一份正式数据编译。这样才能证明人物不会使用自己未见过的信息，而不是只在提示词中承诺“杜绝全知”。

## 反馈闭环

收到真实使用反馈后，先定位主要问题属于以下哪一类：

- **找不到对象或入口**：检查项目菜单、左栏导航、视图切换和窄屏进入路径。
- **对象只能塞进文本框**：检查是否缺少类型化节点、事实、事件、引用或输出卡片。
- **关系看不见或不能修改**：检查是否需要类型化边、证据链接、时间顺序或知情范围。
- **不知道 AI 改了什么**：检查候选与正式数据的区分、接受和拒绝操作以及变更依据。
- **不知道人物为何知道**：检查事实来源、正文证据、观察关系和 Worker 输入预览。
- **运行信息干扰创作或故障不可查**：分别检查主界面的信息层级和执行抽屉的诊断完整性。

每轮反馈至少形成一条“观察 → 根因层级 → 设计变化 → 可操作验收”的记录。例如，“左栏只有工程名”不是补几个图标，而是导航层缺少故事对象；对应变化是让人物、故事、资料和输出进入左栏，验收是在单工程中仍可从左栏到达所有创作工作面。实现完成后使用真实页面复现原始操作，再把结果和仍未解决的问题写回本文或当前实现文档。

局部建议不自动成为产品方向。“做成思维导图”“增加一个说明”“放进设置”等表达先还原为用户真正需要完成的操作，再选择组件。若反馈要求改变正式数据语义、人物可见范围或流水线输入，先修改模型和编译规则；若只是布局、文案或视觉层级，才停留在客户端。这样既能吸收反馈，也不会让连续的局部修补重新长成长表单。

## 迭代方法与路线保护

长期目标以完整创作任务为单位：维护人物各自可知的历史，组织大纲与伏笔，检索并引用原著或网络资料，让研究、人物、导演、分区和编辑 Worker 协作生成可修改的正文。外部 Issue、兼容请求和局部组件升级只有在支撑或阻塞这条主路径时才提高优先级，不能让故事工作室重新退化为互不相连的功能清单。

每个实现纵切片从一个玩家动作开始，并以同一个动作在真实页面完成而结束。例如资料纵切片不是“增加引用类型”，而是“打开原著、定位段落、引用到剧情节点、修改原文后仍能识别当时采用的依据”。类型、协议、测试和文档为这个动作提供可重建证据，不各自扩张成独立项目。已经运行的能力应保留为可继续升级的基础，但实现方式不因为投入过时间就免于重构。

后续优先级按以下顺序判断：

1. 玩家无法完成故事创作主路径，或者已保存内容会丢失、串用或被错误写入模型上下文。
2. 人物认知、事件证据、资料引用、候选接受等故事语义无法被核验。
3. 对象入口被遮挡、状态切换丢失位置、窄屏无法操作等真实交互阻塞。
4. 信息层级、命名、视觉密度和操作效率问题。
5. 不阻塞当前主路径的扩展、兼容和内部运行设置。

反馈记录使用同一组字段，避免只留下结论或情绪描述：

| 字段 | 记录内容 |
| --- | --- |
| 场景 | 玩家原本要完成的任务、页面尺寸和必要前置状态 |
| 观察 | 实际看见或操作到的结果，不先写解决方案 |
| 根因层级 | 数据语义、信息架构、交互、视觉或运行诊断 |
| 设计变化 | 哪个对象、关系、视图或流程需要改变 |
| 验收动作 | 在真实页面中如何证明原问题已经消失 |
| 后续发现 | 验收中新暴露的问题及其优先级，不悄悄扩大本纵切片 |

当前文档描述的是可检验假设，不是不可修改的规格。真实反馈可以改变栏位、视图、组件甚至对象模型；改变后需要同步更新设计原则、当前实现边界和验收动作。这样既不会用“已经写过文档”拒绝新认识，也不会因一次局部反馈丢失人物认知隔离、资料可追溯和正式数据与 AI 候选分层等核心能力。
